## 1. Вердикт коротко

Проект **в рабочем состоянии**: собирается по типам, линтуется без замечаний, тесты зелёные, сервер поднимается и API отвечает. Базовая защита (path traversal, CSRF, туннель, Electron) сделана заметно выше среднего для проекта такого размера.

## 3. Высокий уровень

### H1. Поиск по проекту не работает вообще — 400 на любой запрос

`src/lib/workspace-files.ts:420` (`searchWorkspaceFiles`), `:99` (`readTextState`), `:106`, `:59` (`isTextPath`), `:17` (`IGNORED_DIRECTORIES`)

Воспроизведение (проверено на живом сервере):

```
POST /api/workspace/search  {"query":"workspaceSettings"}
→ 400 {"error":"Binary files cannot be edited as text"}
```

Причина — цепочка из трёх ошибок:

1. `isTextPath` (`:59`) считает текстовым **любой файл без расширения** (`|| !extension`);
2. `IGNORED_DIRECTORIES` (`:17`) не содержит `release/`, хотя это каталог сборки;
3. `readTextState` (`:106`) бросает исключение на NUL-байте, а `searchWorkspaceFiles` не ловит ошибку по отдельному файлу — падает весь обход.

В этом репозитории виновник — `release/linux-unpacked/chrome-sandbox` (15 КБ, бинарник без расширения). Достаточно одного такого файла в любом проекте пользователя.

**Эффект:** кнопка «Поиск по проекту» мертва, а из-за `ide-app.tsx:1116` (`if (!res.ok) return;`) пользователь видит не ошибку, а пустую выдачу — то есть даже не понимает, что фича сломана.

**Исправление:** обернуть чтение файла в `try/catch` внутри цикла поиска; добавить `release`, `out`, `target`, `.turbo` в игнор; не считать файл без расширения текстовым по умолчанию (или проверять первые 8 КБ на NUL); в UI показывать `payload.error`.

### H2. Агент и IDE читают секреты проекта (`.env`, ключи, сертификаты)

`src/lib/workspace-files.ts:54` (`isIgnoredFile`), `:99` (`readTextState`), `:405` (`readWorkspaceFile`)

Проверено:

```
GET /api/workspace/file?path=.env.local
→ 200 {"path":".env.local","content":"DATABASE_URL=\"file:./dev.db\"\r\n"}
```

`isIgnoredFile` фильтрует `.env*`, `*.pem`, `*.key`, `*.p12` только при построении дерева и индекса (`walkDirectory`, `isTextPath`). Прямое чтение через `readWorkspaceFile` идёт в `readTextState` **без этой проверки**, а `read_file` — инструмент агента (`agent-tools.ts`) — вызывает именно `readWorkspaceFile`.

**Эффект:** модель может прочитать `.env`, токены, приватные ключи и отправить их стороннему провайдеру (OpenRouter/OpenAI/…). Это ровно тот класс утечки, от которого защищают шифрование API-ключей в БД.

**Исправление:** перенести проверку `isIgnoredFile` в `readTextState` (единая точка), либо в `readWorkspaceFile` + отдельный явный «показать секрет» с подтверждением пользователя. Инструменту `read_file` — маскировать значения.

### H3. Песочница терминала обходится через `python -m <любой модуль>`

`src/lib/terminal-command.ts:30`

```ts
python: { executable: …, subcommands: new Set(["-m", "--version"]) }
```

Аргумент после `-m` не проверяется. Проверено на живом сервере: `python -m pip --version` → **200 OK, выполнено**.

Отсюда: `python -m pip install <пакет>` (запуск произвольного кода из пакета), `python -m http.server` (сетевой сервер), `python -m venv`, любой установленный модуль. Allowlist даёт лишь видимость ограничения — при этом README заявляет песочницу как защитный механизм.

Рядом: `git diff|show --ext-diff` исполняет внешний diff-драйвер, а `git branch -D` (разрешённая подкоманда) удаляет ветки — для «read-only советника» это не read-only.

**Исправление:** валидировать имя модуля по короткому allowlist (например только `-m pytest`, `-m unittest`), либо убрать `-m` вовсе; для `git` — запретить `-D`/`--ext-diff`; для `node` ограничить `allowRelativeScript` списком каталогов (`scripts/`, `tools/`).

### H4. Автопуш в GitHub отправляет в репозиторий всё, включая секреты

`src/lib/workspace.ts:518` (`pushWorkspaceToGitHub`), `:556` (`git add -A`)

Пайплайн: `git init` → `git add -A` → `commit` → `push`. Проверки наличия `.gitignore`, фильтра секретов и подтверждения нет. При включённом `githubAutoPush` это происходит автоматически после правок файлов (`maybeAutoPushSingleFile`).

Для проекта без `.gitignore` в публичный репозиторий уедут `node_modules`, `.env`, `.env.local`, `*.pem`, служебный каталог `.multi-agent-backups/` с бэкапами исходников и `dev.db` (SQLite с историей чата и событиями).

**Исправление:** перед `add -A` — гарантировать `.gitignore` (создать при отсутствии), жёстко исключать `.env*`, `*.pem`, `*.key`, `dev.db`, `.multi-agent-backups/`, и показывать список файлов на подтверждение (в авто-режиме — как минимум логировать его).

### H5. Снапшот всего проекта каждые 4 секунды и неограниченная история чата

`src/lib/workspace.ts:705` (`messageRows` без `limit`), `src/components/ide-app.tsx:747` (поллинг 4 с)

`getWorkspaceSnapshot` отдаёт **все** файлы с полным содержимым, **все** сообщения чата, события, терминал. Замер: `GET /api/workspace` = 518 958 байт на этом репозитории, при 286 текстовых файлах. UI опрашивает его каждые 4 секунды.

`messageRows = await db.select().from(chatMessages)` — без `limit`, история растёт бесконечно. Каждый новый диалог увеличивает ответ, время сериализации и нагрузку на SQLite — линейно и без потолка.

**Эффект:** на реальном проекте (тысячи файлов, месяцы переписки) это десятки мегабайт каждые 4 секунды — деградация UI, памяти и диска. Сейчас это уже ~500 КБ × 900 раз в час.

**Исправление:** разделить эндпоинты — дерево без контента, контент по требованию; `limit` на сообщения (например 200 последних + пагинация); инкрементальная синхронизация по `updatedAt`/`id`; увеличить интервал или перейти на SSE.

## 4. Средний уровень

**M1. Ошибка поиска скрывается в UI.** `ide-app.tsx:1116` — `if (!res.ok) return;` вместо `setStatus(payload.error)`. Пользователь не узнает о сбое (связано с H1).

**M2. Мобильный токен лежит в JS-доступной cookie и попадает в URL.** `ide-app.tsx:1400` пишет `mobile_access_token` в `document.cookie` без `HttpOnly` (и без `Secure`); мобильное превью открывается как `/api/preview/proxy?token=…` (`mobile/page.tsx:83,140`), а прокси ещё и ставит этот cookie (`preview/proxy/route.ts:47`). Любой XSS в IDE или в отдаваемом прокси HTML = кража токена = постоянный удалённый доступ. Fix: `HttpOnly; Secure; SameSite=Strict` ставить сервером, токен не передавать в query (использовать cookie), прокси — на отдельном origin.

**M3. Гейт `/mobile` — мёртвый код.** `proxy.ts:43` проверяет `/mobile`, но `matcher: "/api/:path*"` (`:80`) до этого пути не доходит. Проверено: `GET /mobile` без токена → 200. Сам API за токеном, но оболочка мобильного UI публична. Fix: `matcher: ["/api/:path*", "/mobile"]`.

**M4. Оркестратор молча правит `package.json` пользователя.** `orchestrator.ts:752` → `ensureBuildDependencies` добавляет `typescript`, `@types/react`, `@types/react-dom`, `vite` и запускает `npm install` в чужом проекте на каждой проверке. Неожиданные изменения зависимостей, сеть, время. Fix: только в отдельном шаге с подтверждением, либо запускать проверки без доустановки.

**M5. Ложный `FAILED` и ложный текст причины.** `orchestrator.ts:1256`: `releaseStatus = allChecksPassed && changedFiles.size > 0 ? "RELEASE_READY" : "FAILED"`. Если модель обоснованно вернула `patches: []` (менять нечего), все проверки прошли — задача всё равно `FAILED`, а summary (`:1265`) говорит «Нет подключённой рабочей папки…», хотя папка подключена. Fix: отдельный статус `NO_CHANGES_NEEDED` и корректный текст.

**M6. `classifyStance` даёт ложные конфликты.** `orchestrator.ts:581` — регулярки по подстрокам: «ошибок нет», «no error», «do not» → `blocker`; «готов» в отрицании → `approve`. Как следствие — фиктивные `CONFLICT_DETECTED` и лишние раунды. Fix: требовать от советника короткий JSON `{"stance":"approve|change|blocker"}`.

**M7. `extractFencedPatches` ломает применение.** `orchestrator.ts:151` — `isNew = /созда|new file|create/` в 200 символах до блока. Слово «create» в обычном тексте («create a helper») помечает существующий файл как `create` → `applyWorkspacePatch` падает «File already exists» → патч не применяется вообще. Плюс любой листинг в ответе модели может быть записан как файл. Fix: определять операцию по факту (`exists ? modify : create`), а не по тексту.

**M8. Гонки в управлении превью.** `preview-process.ts:77,103,106`: `previewUrl` пишется сразу после `spawn`, до того как сервер начал слушать (прокси отдаёт 502); обработчик `exit` старого процесса делает `child = null`, обнуляя **новый** процесс при быстром рестарте — статус врёт, процесс не убивается. Порт по умолчанию 4173, а `npm run dev` у Vite слушает 5173 — пустое превью. Fix: ждать готовности порта, привязывать обработчики к конкретному экземпляру, определять порт из конфига проекта.

**M9. `BEGIN IMMEDIATE` на общем соединении.** `workspace-files.ts` (`renameWorkspaceEntry`) вызывает `sqlite.exec("BEGIN IMMEDIATE")` вручную на общем `DatabaseSync`. Параллельный запрос попадёт внутрь чужой транзакции, второй rename получит «cannot start a transaction within a transaction». Fix: `db.transaction(...)`.

**M10. Авто-цикл — мёртвый код.** `workspace.ts:1953` (`runAutoCycleBackground`) нигде не вызывается (проверено поиском по `src`). ~100 строк логики review → fix → `RELEASE_READY` не исполняются. При этом переключатель AUTO в UI меняет только `settings.autoApprove`, который читает лишь `/api/orchestrate/*`. То есть в чате AUTO ничего не делает — это осознанное решение (комментарий в `streamWorkspaceMessage`), но код остался и вводит в заблуждение. Fix: удалить либо подключить осознанно.

**M11. Один медленный агент блокирует весь раунд.** `workspace.ts` (`runAgentRound`): агенты идут **последовательно** с задержкой 1.5 с, лимит 5 минут на агента. При 5 агентах одно сообщение может занять 25+ минут. Плюс `looksLikeTask` в чате Главного синхронно запускает полный командный раунд внутри запроса пользователя. Fix: параллельный запуск с ограничением конкурентности, стриминг прогресса.

**M12. Агент выпадает из команды на 10 минут по любой ошибке в логе.** `workspace.ts:1311` (`getOfflineAgentNames`) берёт последние 50 записей `system_events` и считает источник офлайн при `level === "error"`, включая источники `terminal`, `github`, `preview`, `auth`. Один таймаут — и агент исключён из раундов на 10 минут без ручного сброса. Fix: фильтровать по `source ∈ agents.name` и хранить состояние явно.

**M13. Двойное экранирование в промптах.** `workspace.ts:1259` — `replace(/\\s+/g, " ")` (литеральный обратный слэш + `s`), `:1297` — `\\n\\n` вместо перевода строки. Следствие: сводка истории не сжимает пробелы, вложения приклеиваются к тексту литеральными `\n`. Fix: заменить на `/\s+/g` и `\n\n`.

**M14. Роль агента — соглашение, а не авторизация.** `api/workspace/patch/route.ts` принимает `actorAgentId` от клиента, `assertMainAgent` проверяет только, что у этого id роль `main`. Любой локальный скрипт (и мобильный клиент с токеном) может писать файлы «от имени главного». Для локального приложения допустимо, но стоит хотя бы подписывать запросы сессионным секретом.

**M15. Ротация мобильного токена доступна снаружи.** `api/settings` (PATCH) входит в список remote-route (`proxy.ts:67`), значит удалённый пользователь с токеном может **сменить** `mobileAuthToken` (в т.ч. на свой) — `mobile/settings.tsx:41`. Fix: менять токен только с loopback.

**M16. Туннель держится на in-memory флаге.** `mobile-auth.ts` считает запрос локальным по заголовку `Host`; при включённом туннеле полагается на `isTunnelActive()` из `tunnel-state.ts` (переменная модуля). Проверил `localtunnel`: клиент **не** переписывает `Host` (трансформация включается только при явном `local_host`, а его никто не передаёт) — значит защита работает. Но вся модель безопасности туннеля опирается на один булев модуль-скоуп: при разделении бандлов роутов (или переезде на edge) флаг станет `false`, и трафик из туннеля начнёт считаться локальным. Плюс сравнение токена не constant-time (`suppliedToken === configuredToken`). Fix: требовать токен для любого не-loopback соединения по признаку TCP-соединения, а не по заголовкам; `crypto.timingSafeEqual`.

## 5. Низкий уровень

1. `terminal-command.ts` (`tokenize`) запрещает `..` **в любом месте** строки и слова `cmd|sh` — режутся легитимные команды (`npm test -- --testPathPattern`, файл `cmd.ts`).
2. `MIN_MAX_ITERATIONS = 5` (`orchestrator.ts:63`) — попросить 1–4 итерации нельзя.
3. `.multi-agent-backups/` пишется в корень проекта пользователя — мусор в чужом репозитории.
4. `db/index.ts` собирает строки через `Object.values(row)` — при появлении JOIN с одноимёнными колонками данные разъедутся (сейчас JOIN нет — риск латентный).
5. `connectWorkspaceDirectory` делает `db.delete(projectFiles)` дважды подряд.
6. `pushMessage` (`workspace.ts:429`) проглатывает сообщения агента, похожие на техническую ошибку (`isTechnicalErrorText`) — реальный ответ может не попасть в чат, хотя событие `agent_done` уйдёт.
7. Дрейф документации: README заявляет Next.js 15 и `better-sqlite3`, фактически Next 16.2.6 и `node:sqlite` (`DatabaseSync`).
8. Тестами покрыты только парсеры (пути, команды, патчи, SSE — 64 теста). На `workspace-files.ts`, `orchestrator.ts`, `provider-gateway.ts` тестов нет — именно там сосредоточены найденные дефекты.

## 6. Что сделано хорошо (проверено)

- **Path traversal** закрыт на всех проверенных входах: `..`, абсолютные пути, Windows-диски → 400. Симлинки отсекаются (`assertNoSymlinkBetween`).
- **CSRF** работает: POST с `Origin: https://evil.example` → 403; `Sec-Fetch-Site` учитывается.
- **Туннель**: не-loopback запрос без токена → 403/503, `X-Forwarded-For` намеренно не используется.
- **Allowlist терминала** блокирует `npm install <пакет>`, неизвестные `npm run`-скрипты, package-manager флаги (`--exec`, `-p`), lifecycle-скрипты.
- **Electron**: `contextIsolation: true`, `sandbox: true`, `nodeIntegration: false`, `guardNavigation`, `setWindowOpenHandler` → deny + `shell.openExternal` только для http(s).
- **Секреты в БД**: AES-256-GCM (`enc:s2:`), ключ вне репозитория; снапшот отдаёт только `apiKeysConfigured`, значения пустые (проверено: 588 байт ответа).
- **Патчи**: атомарное применение с журналом и компенсирующим откатом, бэкапы перед удалением, `expectedHash` от гонок.
- **Провайдеры**: ретраи с `Retry-After`, fallback-модели, idle-timeout на SSE, аккумулятор фрагментированных `tool_calls`, редактирование ключа в тексте ошибки (`redact`).

## 16. Team mode и установщик — 15.11.2026

### Как работает Team mode

Флаг `team_mode` в настройках (по умолчанию выключен), миграция `0013_team_mode.sql`. Когда включён:

1. После решения Главного **каждый советник готовит патчи только для своей зоны**: UI/UX — компоненты, страницы, стили; архитектор — `src/app/api`, `src/lib`, `src/db`; тестер — `*.test.*`; секурити — `proxy`, `auth`, `middleware`.
2. Патчи сливаются: **решение Главного выигрывает при конфликте**, чужие зоны и пересечения отбрасываются и попадают в событие `CONFLICT_DETECTED` (видно в панели оркестратора).
3. Всё применяется одним атомарным набором — как и раньше, с журналом и откатом.
4. При падении проверок путь из лога (`src/lib/x.ts`) резолвится в владельца зоны, и **fix-запрос уходит ему**; если владельца нет или он ничего не вернул — работает текущая логика с Главным.

Файлы: `src/lib/team-scopes.ts` (зоны, `pickOwner`, `extractFilePaths`, `mergeTeamPatches`) — 12 тестов; интеграция в `orchestrator.ts` через `collectTeamPatches()` и `requestOwnerFix()`.

Проверено: миграция применяется на живой базе, `PATCH /api/settings {"teamMode":true}` сохраняется и читается обратно, `tsc`/`eslint` чистые, **125 тестов** зелёные.
